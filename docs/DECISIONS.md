# Decisions

The scope of the tool is the one stated in the README: start at every untrusted `${{ }}` expression, follow the value through `env:`, `with:`, step outputs, job outputs and into the called action, and end each chain in one of five verdicts (`SHELL`, `SPOOF`, `SUSPECT`, `DIES`, `UNKNOWN`). Everything below is a choice this codebase made where that scope left the mechanism open, with what it closes. Numbered so a later change can point at the entry it replaces.

1. **Two modules beyond the planned layout: `model.py` and `yamlload.py`.** The planned modules (`sources`, `workflow`, `propagate`, `sinks`, `actions`, `report`, `cli`) would otherwise import each other for the shared dataclasses and the line-aware loader. Closes: import cycles.

2. **YAML 1.1 keys keep their literal text.** PyYAML turns the plain scalars `on`, `off`, `yes`, `no` and `null` into booleans or `None` when used as keys. The loader keeps the text of any such key, not only `on`. Values are left as PyYAML reads them; a `with:` value of `yes` carries no expression either way. Closes: the `on:` trap and its siblings.

3. **One chain per (source occurrence, terminal).** A value used by two steps yields two chains that share an occurrence id. Within one `run:` block a value use (`DIES`) is not reported for a variable that also reaches a finding in the same block; the finding wins. A "never read" chain is emitted only for an occurrence that produced no other chain. Closes: what "one chain per tainted source" means when the value fans out, and the noise a fan-out would otherwise print.

4. **A single-line write of a tainted value to `$GITHUB_OUTPUT` or `$GITHUB_ENV` is `SPOOF`.** The runner parses those files as `key=value` lines; a value containing a newline adds keys. The README models the static-delimiter heredoc as the finding; the one-line form is the same bug with fewer characters. Closes: `echo "k=$V" >> "$GITHUB_OUTPUT"`.

5. **A dynamic delimiter that cannot be proven random is `UNKNOWN`, not `SPOOF` and not `DIES`.** `EOF_${GITHUB_RUN_ID}` is predictable but the tool does not model predictability; it names what it could not prove. Closes: guessing on delimiters.

6. **Random sources recognised in a delimiter or in the assignment feeding it:** `$RANDOM` (with or without braces), `openssl rand`, `uuidgen`, `/dev/urandom`, `mktemp`, `head -c`, `secrets.token`, `date +%s%N`, `$$`. Assignments are tracked forward through the script. Closes: the random-delimiter fix shape (`openssl rand -hex 16`) and its common variants.

7. **Two heredocs, told apart.** A shell heredoc (`cat <<EOF ... EOF`) is the script's own text; its body expands `$VAR` unless the delimiter is quoted (`<<'EOF'`), and single quotes inside the body do not stop expansion. The runner's file-format heredoc (`key<<DELIM` ... `DELIM` written into `$GITHUB_OUTPUT`) is what makes a write spoofable. The scanner tracks the second as an open block across `echo` lines, brace groups (`{ ... } >> "$GITHUB_OUTPUT"`) and shell heredoc bodies. Closes: the three ways the documented multi-line output pattern is written.

8. **Extra `SHELL` patterns beyond `eval`, `bash -c`, `source`, `xargs` and `| sh`:** a tainted value in command position (`$V --flag`), an interpreter `-c`/`-e` string (`python -c`, `node -e`), and a heredoc body fed to a shell or interpreter (`bash <<EOF`, `python - <<EOF`). Known false positive, documented in the README: `bash -c 'x "$1"' _ "$V"`. Closes: three shapes that are code execution by the same mechanism as the listed ones.

9. **A prefix of a source is tainted.** `toJSON(github.event)`, `github.event.pull_request` and `github` itself carry the untrusted fields inside them and are reported with the note `contains untrusted fields`. Closes: the `toJSON` shape.

10. **`inputs.*` depends on where it is read.** In a top-level workflow it is the same as `github.event.inputs.*` (semi-trusted, printed, never counted). Inside a composite action or a called reusable workflow it is the caller's `with:` taint. There is no flag to count semi-trusted chains; the CLI stays as designed. Closes: the two meanings of `inputs`.

11. **Environment inheritance is followed into composite steps, and into JavaScript only by name.** A composite step runs in the same process environment, so a job `env:` reaches its `run:` lines with no extra hop. A JavaScript file is checked for `process.env.NAME` (dot, bracket and destructuring forms); if it names the variable the heuristic runs, otherwise nothing is claimed. Docker actions and binaries are not followed. Closes: how far an `env:` value is chased.

12. **Opaque actions are recorded per taint occurrence.** When an action cannot be read (not vendored, docker, unsupported `runs.using`, missing `main`), every tainted variable visible to that step is marked as having run through it. A variable nothing reads by name then ends as `UNKNOWN` naming those actions, instead of `DIES`. A variable defined at workflow level sees the opaque steps of every job. Closes: the never-read verdict being honest about what could have read the variable.

13. **Script following.** Invocations recognised: `bash|sh|zsh|dash|ksh|node|python|python3|source|. <path>`, and a bare `<path>` ending in `.sh`, `.bash`, `.js`, `.mjs`, `.cjs` or `.py`. Path tokens are resolved after substituting `$GITHUB_ACTION_PATH`, `$GITHUB_WORKSPACE`, `${{ github.action_path }}`, `${{ github.workspace }}` and any variable assigned from the `dirname "$0"` / `dirname "${BASH_SOURCE[0]}"` idiom; relative paths are tried against `working-directory`, the workspace, the invoking script's directory and the action directory, in that order. Shell files are scanned with the same rules, JavaScript files with the heuristic, anything else is `UNKNOWN`. Tainted arguments map to `$1`, `$2`, ..., `"$@"` and `$*`. Each followed file counts one level of depth and is on the cycle stack by absolute path. Closes: the "shell script that only delegates" hop, where a `run:` line hands the value to another file it runs.

14. **JavaScript heuristic, in order:** `shell: true` anywhere is `SUSPECT`; `execSync(` anywhere is `SUSPECT`; `exec(` with a template literal whose `${...}` names an identifier bound from `getInput(...)`, `process.env` or `process.argv` is `SUSPECT`; `exec(` present but not tied is `UNKNOWN`; `spawn(`/`execFile(`/`spawnSync(`/`execFileSync(` followed by an array literal is `DIES`; otherwise `UNKNOWN: JavaScript action, no shell pattern matched`. `SUSPECT` and `DIES` carry the `heuristic` flag and render as `SUSPECT (heuristic)` / `DIES (heuristic)`; `UNKNOWN` is a refusal, not a guess, and is not labelled. Closes: the JavaScript-action outcome, made mechanical instead of a judgement call.

15. **Propagation beyond the README's four hops (`env:`, `with:`, step and job outputs), because the machinery was already there:** `needs.J.outputs.Y` across jobs (jobs analysed in dependency order), `strategy.matrix` built from an expression tainting `matrix.*`, a composite action's `outputs:`, a reusable workflow's `on.workflow_call.outputs`, and a composite input `default:` that holds an expression. Closes: the common "moved to another job" and "moved behind an output" shapes.

16. **The step-outputs over-approximation also fires when the write happens in a followed script.** The flag propagates up from the script to the step. Variables set through `$GITHUB_ENV` are not tracked into later steps beyond that rule; `$GITHUB_PATH` is ignored. Closes: where the over-approximation applies.

17. **Non-POSIX shells are `UNKNOWN`.** A step with `shell: pwsh`, `powershell`, `python` or `cmd` that mentions a tainted variable by name is reported as not analysed. `shell: bash -e {0}` and friends are analysed as bash. Closes: silent misses on other shells.

18. **Exit code 2 for usage and parse errors** (missing path, no workflow files, invalid YAML, `--fetch` without a directory), so a broken invocation is never mistaken for a clean scan. Closes: the exit code table.

19. **A directory argument scans `<dir>/.github/workflows/*.y*ml` when that folder exists, otherwise `<dir>/*.y*ml`, sorted.** No recursion into arbitrary trees. Closes: what "or dir" means on the command line.

20. **`--fetch` runs four git commands per missing `owner/repo@ref`:** `git init`, `git remote add origin https://github.com/owner/repo.git`, `git fetch --depth 1 origin <ref>`, `git checkout FETCH_HEAD`. That works for tags, branches and commits alike. The ref is used as a directory name verbatim. The command runner is injectable; the tests exercise the sequence with a fake and never touch the network. Closes: the `--fetch` opt-in (a shallow clone the caller asks for explicitly) without a branch-only limitation.

21. **File paths in hops are shown relative to the current directory when the file is under it, absolute otherwise.** Closes: readable output and clickable paths in editors.

22. **Reasons always name the pattern that matched**, and where the evidence is a file other than the workflow, the file and line. Closes: a verdict a reader can check in the source it points at.

23. **House extras, beyond the analyser itself:** a `Dockerfile`, a mermaid architecture diagram in the README, and a test that compares the README hero block with the demo output byte for byte so a stale README fails the build. Closes: the portfolio standard.

The entries below came out of an adversarial review of the first build. Each one names the entry it amends.

24. **A one-line group with a redirect to the runner file is the multi-line group with fewer characters.** `{ echo "k<<EOF"; echo "$V"; echo "EOF"; } >> "$GITHUB_OUTPUT"` (braces or a subshell, `>>`, `>` or `| tee`) is split into its fragments and every fragment inherits the closing redirect, so the static-delimiter block is tracked across them and the write is `SPOOF`. A fragment that re-parses the value (`{ eval "$V"; } >> ...`) is still `SHELL`. Amends 7, which only tracked the block when the braces stood on their own lines. Closes: the shortest form of the second bug in the modelled finding, which the first build reported as `DIES`.

25. **JavaScript action outputs are over-approximated, like run-step outputs.** A node action that received a tainted `with:` input, or whose main file names a tainted variable through `process.env`, taints every output it declares; when it declares none, every output name (`*`). `github-script` taints `*` (its `result` and any `core.setOutput`) when a tainted expression is expanded into the script or the script names a tainted variable. The hop says `over-approximation`; nothing inside the JavaScript is followed to prove which output got the value. A clean input taints nothing. Extends decision 3 (one chain per source occurrence and terminal) to the two kinds of step it did not cover. Closes: `${{ steps.x.outputs.result }}` after a JavaScript action, the classic injection one step later, which the first build reported only as the verdict inside the action.

26. **The step-outputs rule also fires from a followed JavaScript file and from an interpolated write.** A followed `.js` that mentions `GITHUB_OUTPUT`, `GITHUB_ENV`, `setOutput(` or `exportVariable(` reports the write back to the step; an expression expanded straight into a script that writes the runner file (`echo "x=${{ ... }}" >> $GITHUB_OUTPUT`) taints the step's outputs as well as being `SHELL`. Amends 16, whose promise covered shell scripts only. Closes: a composite whose script delegates the write to Node.

27. **`::set-output` is a write and a `SPOOF`; `::set-env` is neither.** The runner still honours `::set-output name=k::$V` with a deprecation warning, and a newline in the value starts a new workflow command, so it gets the same verdict as the one-line write and counts as writing outputs for decision 3. `::set-env` has been disabled by the runner since 2020 and is left as a value use. Closes: the deprecated form of the same bug.

28. **The shell of a step is inherited.** Step `shell:`, else the job's `defaults.run.shell`, else the workflow's, else `pwsh` when `runs-on` is a `windows-*` runner or a label list containing one. A `runs-on` that is an expression is read as Linux. Amends 17, which read only the step. Closes: a Windows job or a `defaults: run: shell: python` job being scanned as bash and ending in a confident `DIES`.

29. **A `uses:` reference is validated before anything is resolved, and both roots are enforced.** Owner and repo match `[A-Za-z0-9_.-]+` and never contain `..`; path segments are relative, non-empty and free of `..` and backslashes; the ref may contain `/` (`releases/v1` is a documented form) but never `..`, a leading `-` (a git option) or a leading `/`. Anything else is `invalid` and ends as `UNKNOWN: could not be parsed`. The local resolver returns a directory only when it resolves, symlinks followed, under `--actions-dir` (or under the repository for `./path`). `--fetch` checks the same before any `mkdir` or `git` call and raises a named error otherwise; the ref is passed to `git fetch` after `--`. Amends 20, which used the ref as a directory name verbatim. Closes: `uses: x/y@../../../outside` reading an action outside the directory, and with `--fetch`, creating directories or running git anywhere.

30. **Unreadable input is reported and skipped, never a traceback, and exit 2 means no file was read.** Not-UTF-8 (`UnicodeDecodeError`), a YAML document nested beyond what the parser handles (`RecursionError`) and an unreadable action manifest all become the named errors (`WorkflowError`, `YamlError`, `ActionError`). In a directory scan each failure goes to stderr and the rest is scanned; exit 2 only when nothing could be read, otherwise the exit follows the verdicts. A reusable workflow with broken YAML is `UNKNOWN` naming the file. Amends 18 and 19. Closes: an exit 1 that was a crash colliding with an exit 1 that was a finding, and one empty file aborting a whole directory.

31. **A program string that names a tainted variable without expanding it is `UNKNOWN`.** On a line with `python -c`, `node -e`, `bash -c`, `perl -e` or `envsubst`, a tainted name that the outer shell does not expand (`os.environ['BODY']`, a single-quoted `'$BODY'` handed to `envsubst`) is reported as `interpreter string mentions the variable by name`, not as never read. A real expansion on the same line is still `SHELL`. Closes: `DIES: BODY is never read by name` printed under a line that spells BODY.

32. **A random-delimiter write to `$GITHUB_ENV` is `UNKNOWN`, not `DIES`.** The variable it defines is visible to every later step and the tool does not track it there (see the README limits); calling that `DIES` claimed more than the tool knows. The same write to `$GITHUB_OUTPUT` stays `DIES`, because outputs are tracked through decision 3. Amends 5 and 16 in wording. Closes: a confident `DIES` above a later `eval "$TITLE"`.

33. **Fewer things count as random.** `$$` is a PID, `head -c` reads a file, `date +%s%N` is a clock; none is randomness and all are dropped from decision 6. Kept: `$RANDOM`, `openssl rand`, `uuidgen`, `/dev/urandom`, `mktemp`, `secrets.token`. A delimiter built from a dropped source is `UNKNOWN` (decision 5), never `SPOOF`. Amends 6. Closes: `EOF_$(head -c 4 /etc/hostname)` passing as random.

34. **Every scalar under `strategy.matrix` is read for expressions**, not only the form where the whole matrix is one expression: `include: ${{ fromJSON(...) }}` and an axis built from an expression taint `matrix.*` the same way. Amends 15. Closes: the `include:` shape.

35. **The CI proves detection, not only cleanliness.** A second self-test step runs the tool on two fixtures it must flag and asserts exit 1 with `SHELL` and `SPOOF` in the output; `tests/test_self_ci.py` runs the same script. The hero fixture is the `helper` action and `helper-cli`, names that belong to nothing real. Amends 23. Closes: a self-scan that would pass for a tool that finds nothing.

The entries below came out of the second adversarial review, which re-broke the fixed shapes with layout variants. Each one names the entry it amends.

36. **A group is tracked as a construct, not matched as a layout.** A `{` or `(` in command position (the start of a line, or after `;`, `&&`, `||`, `|`, `&`, another opener, or one of `do`, `then`, `else`, `if`, `elif`, `while`, `until`, `!`, `time`) opens a group whatever follows on the same line; the matching close is found by keeping a stack of openers across lines (a `}` closes only as a word of its own, a `)` only matches a `(`, `${`, `$(`, `<(`, `>(` and brace expansions never open a group, heredoc bodies are skipped), wherever it sits: at the end of a body line, on its own line, after `2>&1`, before `; done` or `; fi`. What follows the close up to the next separator is the trailer; a runner-file target or a pipe into a shell in the trailer applies to every command inside, nested groups inherit it, the prefix before the opener and the rest after the trailer are scanned on their own, and the trailer itself is scanned (a `case` pattern's `(a) cmd;;` lands there). The body goes through the same scanner as top-level lines, so `{ eval "$V"; }` in any layout is `SHELL`, not `SPOOF`. Amends 7 and 24, which recognised exactly two layouts. Closes: the two-line, open-with-content, close-on-last-line, `[ ... ] && { }`, `for ...; do { }; done`, `if ...; then { }; fi` and nested forms, all of which the previous build reported as `DIES`.

37. **Every redirect and tee form is a target, on a simple line and as a group trailer.** `>>`, `>`, `1>>`, `1>`, `2>>`, `&>>`, `&>`, `>|`, `2>&1 >>`, `| tee -a`, `| tee --append`, `| sudo tee -a` and `tee` with several options all name the runner file when followed by `$GITHUB_OUTPUT` or `$GITHUB_ENV`. The `&` of `2>&1`, `&>` and `<&` is no longer a command separator, so `echo "k=$V" 2>&1 >> "$GITHUB_OUTPUT"` is one pipeline. `2>>` writes only stderr and is accepted anyway: the file is named, the tool does not reason about which stream carried the value. Amends 4 and 24. Closes: `1>>`, `&>>`, `tee --append` and `>|` passing as `DIES`.

38. **The runner file reached through a variable or a descriptor is still the runner file.** `OUT="$GITHUB_OUTPUT"` (quoted, unquoted, braced, `export`, an alias of an alias) makes `>> "$OUT"` a target from that line on; `exec 3>>"$GITHUB_OUTPUT"` (or through such an alias) makes `>&3` and `1>&3` targets. A variable assigned any other path, or a descriptor opened on any other file, is not. Both were listed as unhandled in the review with the choice of implementing or documenting; implemented, because the tracking is a dictionary each and the shapes appear in real workflows. Closes: the indirect target and the `exec` descriptor.

39. **A step in any shell that writes the runner file taints its outputs.** The over-approximation of decision 3 applied only to bash-like steps; a `pwsh` step doing `"r=$env:BODY" >> $env:GITHUB_OUTPUT`, a `python` step opening `os.environ["GITHUB_OUTPUT"]`, or a `cmd` step, with a tainted variable in env, left `${{ steps.x.outputs.r }}` clean one step later. The step itself stays `UNKNOWN` (its script is not analysed); its outputs are tainted by the file's name in the script. Amends 17 and the README's propagation rule, which promised this without restricting it to bash. Closes: `eval "${{ steps.w.outputs.r }}"` after a PowerShell write.

40. **A JavaScript action taints every output name, declared or not.** `core.setOutput("secret", ...)` needs no declaration; a manifest that declares `result` and sets `secret` at runtime left `${{ steps.x.outputs.secret }}` clean. `*` is now seeded alongside the declared outputs. A declared output is carried by its own hop (`outputs.result`), and `*` only adds occurrences that hop did not already carry, so a chain is never reported twice. Amends 25. Closes: the undeclared output.

41. **Every file the tool opens is checked against a root, after resolving symlinks.** The manifest against its action directory (a symlinked `action.yml` pointing elsewhere is `UNKNOWN: ... resolves outside the action directory (symlink) and is not read`); `runs.main` against the action directory; a followed script against the workspace, the invoking script's directory and the action directory (a candidate that exists but resolves elsewhere is `UNKNOWN: ... resolves outside the scanned roots`); a literal absolute path is never followed (`$GITHUB_ACTION_PATH/...` and `$(dirname "$0")/...` substitutions produce absolute paths that are checked like any other); a `working-directory` that resolves outside the workspace is never entered. The workflow files named on the command line are the one thing read as given. Amends 29, whose check stopped at the action directory. Closes: reading, and printing lines from, a file outside the scanned roots through a symlink, `../`, an absolute path or `working-directory`.

42. **A `runs-on` expression is resolved against the matrix, and an undetermined runner is `UNKNOWN`.** `runs-on: ${{ matrix.os }}` with every value of `os` (axis, `include`, `exclude`) a non-Windows label is analysed as bash; any Windows value, a matrix that is itself an expression, a key that does not exist, or a reference that is not `matrix.*` makes the default shell undetermined, and a step that mentions a tainted variable is `UNKNOWN` saying so. The mapping form `runs-on: {group: ..., labels: [...]}` is read by its labels. A step `shell:` still wins. Amends 28, which read every expression as Linux. Closes: a Windows-only matrix ending in a confident `DIES`; the last README limit without a pinning fixture.

43. **`process.env` through an alias.** `const env = process.env` (also `let`, `var`) followed by `env.NAME` or `env["NAME"]` counts as reading `NAME`, in `js_references_env` and in the heuristic's binding of identifiers to `exec` templates; destructuring already did. Amends 11. Closes: an action reading the environment through an alias reported as never read.

44. **More interpreters, and standard input.** `php -r`, `deno eval` and `bun -e` join the program-string patterns. A tainted value piped into a bare interpreter, or into one given `-`, runs as code (`| python3`, `| node -`, `| php`, `| ruby`, `| perl`, `| deno run -`); an interpreter given a script file or `-m` does not, and is not flagged. `deno run -` and `php` also count as heredoc consumers. Amends 8 and 31. Closes: the three interpreters missing from the list, and `echo "$V" | python3` passing as a value use.

45. **Owner and repo may not start with `-`.** `-owner/repo@v1` would reach git as an option in `--fetch`. Amends 29. Closes: the leading dash.

46. **The shell is read by its basename.** `shell: /bin/bash -e {0}` is bash; `shell: /usr/bin/pwsh` is pwsh. Amends 17 and 28. Closes: a full path to bash ending as `UNKNOWN: shell: /bin/bash`.

The entries below came out of the third adversarial review, which broke the shell sinks and the group tracker with full paths, continuations and redirected compounds. Each one names the entry it amends.

47. **A shell or interpreter is matched by its basename, behind a path or a wrapper.** `/bin/bash -c`, `/usr/bin/env bash -c`, `sudo /bin/bash -c`, `echo "$V" | /bin/sh`, `| /usr/bin/python3` and `bash -o pipefail -c` (an option that takes an argument before `-c`) are all `SHELL`; a full path whose basename is not a shell (`/usr/local/bin/mytool -c`) stays a value. Amends 8, whose lookbehind `(?<![\w/-])` rejected a leading path and whose pipe patterns needed the bare word right after `|`. Closes: `bash -c "$V"` moved behind its absolute path passing as `DIES`.

48. **A pipe into an interpreter is still a pipe into an interpreter with a tail.** `| python3 2>/dev/null`, `| python3 > out.txt`, `| python3 -u`, `| python3 -I -`, `| python3 - arg`, `| sudo -E python3` and `| env python3` run standard input as code; `-W`/`-X` carry an argument and still count, while a script file, `-m module` or `python3 script.py 2>/dev/null` do not. Amends 44, whose `\s*$` anchor was defeated by anything after the interpreter. Closes: a redirect after the interpreter turning `SHELL` into `DIES`.

49. **A heredoc piped to an interpreter given a script file is a value.** The heredoc-consumer test now requires the same bare-or-`-` tail for interpreters as the pipe patterns (`cat <<EOF | python3 parse.py` and `| node app.js`, `| python3 -m json.tool`, `| perl -ne '...'` are values); a shell consumer stays unanchored, and `cat <<EOF | python3` (bare) stays `SHELL`. Amends 7 and 44. Closes: a heredoc feeding a fixed script reported as code execution.

50. **A value only piped into a fixed single-quoted program is data.** When a tainted variable is only on the left of a pipe and the interpreter's `-c`/`-e`/`-pe`/`-ne` string on the right is single-quoted and does not name it (`echo "$V" | perl -pe 's/x//'`, `| python3 -c '...sys.stdin...'`, `| node -e '...'`, `| sed -e '...'`), the program reads the value as input, not code: `DIES`. A double-quoted program that names the value (`perl -e "print $V"`) or the value inside the program string is still `SHELL`. Amends 8. Closes: the sanitiser idiom reported as an injection.

51. **A process substitution given to a shell or interpreter is execution.** `bash <(echo "$V")` runs the substituted output as a script, so it is `SHELL` naming the process substitution rather than `UNKNOWN: script <(echo could not be located`. Amends 8 and 13. Closes: a value executed through `<(...)` reported as an unlocatable script.

52. **More command positions.** A tainted value runs as the command not only after `exec`/`sudo` but after `env FOO=1`, an inline assignment `FOO=1`, `nohup`, `time`, `!`, `if`/`while`/`until`/`then`/`else`/`do`, and after a `|` pipe stage. An assignment whose value is a command substitution (`x=$(echo "$V")`) is not command position. Amends 8. Closes: `env FOO=1 "$V"` and `if "$V"; then` passing as a value use.

53. **`|&` is a pipe.** The separator no longer splits the `&` of `|&`, and the pipe patterns accept it, so `echo "$V" |& bash` is `SHELL`. Amends 8. Closes: `|&` cut at the `&` and read as a background command.

54. **A group closing with a continuation on its line joins the trailer with the lines below.** When a group closes at some column and the rest of that line ends in `\`, `|` or `&&`, the trailer is built across the following lines (`} \` then `>> "$GITHUB_OUTPUT"`, `} |` then `tee -a`, `} |` then `bash`, `} >> \` then the target). Amends 36, which read the trailer only up to the end of the closing line. Closes: a redirect split off the closing line turning `SPOOF` into `DIES`.

55. **A `case` pattern inside a subshell does not close it.** The close scanner tracks `case`..`esac` depth across lines and ignores a `)` that terminates a pattern (one at the stack depth the case opened at) so `( ... case X in a) ...;; esac ... ) >> "$GITHUB_OUTPUT"` stays one subshell. The brace-group form already worked because a `)` never matches a `{`. Amends 36. Closes: `a)` inside a redirected subshell closing the subshell early and dropping the target.

56. **A redirected `for`/`while`/`until`/`if` block is a group.** When the `done`/`fi` line carries a redirect to the runner file or a pipe into a shell, the whole body inherits it (`for k in a b; do echo "k=$V"; done >> "$GITHUB_OUTPUT"`, `done | tee -a`, `while ...; done >> ...`, `fi >> ...`). The block is found by keyword-nesting depth, heredoc bodies skipped; a `done`/`fi` with no such trailer (`done < list.txt`, `> /dev/null`) leaves the body scanned as before. Amends 36. Closes: a compound whose terminator carries the redirect reported as `DIES`.

57. **A self-hosted runner with no OS label is undetermined.** `runs-on: [self-hosted]` can be any platform, so a tainted mention is `UNKNOWN` about the shell rather than analysed as bash; `self-hosted` alongside a `linux`, `ubuntu` or `macos` label is analysed as bash, and a `windows` label is `pwsh`. Amends 42. Closes: a self-hosted Windows runner ending in a confident `DIES`.

The four shapes below are known and left, rare enough not to earn a pattern; the fixtures do not pin them, and the README's "matched by pattern, not parsed" line covers them.

58. **Rare shapes left after the third review.** `n=$((1<<2))` inside a redirected group is misread as a heredoc opener (`<<2))`), so a later tainted `echo` in that group can drop to `DIES`; a redirect on a function definition (`foo() { ...; } >> file`) is not carried to the call; a test-only reference inside a redirected group (`{ [ "$V" = x ] && echo k; } >> "$GITHUB_OUTPUT"`) is reported `SPOOF` though that line writes nothing; and an arithmetic line can carry a slightly wrong reason string. All four are low-frequency and none is a silent miss on a claim the README makes.

The entries below came out of the fourth adversarial review, which re-broke the pipe tail, the group opener and the sanitiser rule with one more token each. Each one names the entry it amends.

59. **A pipe into an interpreter ends at the next pipe stage, not only at the end of the line.** `echo "$V" | python3 | tee log`, `| python3 2>&1 | tee log`, `| node - | tee log`, `| php | cat`, `| deno run - | tee log` and `cat <<EOF | python3 | tee log` run standard input as code: the interpreter tail now ends at the end of the pipeline or before a `|`, so a following stage no longer defeats the match, and `| python3 script.py | tee log` still does not count. Amends 48, whose `\s*$` anchor was defeated by a second stage. Closes: a `tee` after the interpreter turning `SHELL` into `DIES`.

60. **An arithmetic `((` is not a subshell.** `for ((i=0; i<3; i++))`, `while (( n ))` and `if (( n > 1 ))` open no group: the group opener skips a `(` that follows or precedes another `(`, and the close scanner pushes both as non-group openers so their `))` pops them without closing an enclosing group. The compound then goes through the redirected-block rule of 56, so `done >> "$GITHUB_OUTPUT"` after an arithmetic `for` is `SPOOF` and `fi | bash` after an arithmetic `if` is `SHELL`. Amends 36 and 56. Closes: the second `(` of `for ((` read as a subshell that closed at the first `)`, leaving the body scanned with no target.

61. **The by-name rule reads only the program string.** The check for a program string naming a tainted variable now looks from the program-string match on (`python -c`, `bash -c` and their kin; from column 0 for `envsubst`, whose program text is its standard input), both for the name and for what the shell expanded there. A value piped in from the left is neither a mention nor an expansion that hides one: `echo "$V" | python3 -c 'import os; os.system(os.environ["V"])'`, `| perl -e 'system($ENV{V})'` and `| node -e '...process.env.V...'` are `UNKNOWN` naming the variable, while `echo "$V" | perl -pe 's/x//'` and `| python3 -c '...sys.stdin...'` stay `DIES`. Amends 31 and 50; 50 counted the left-hand expansion and so suppressed the `UNKNOWN`. Closes: `DIES` printed under a program string that spells the variable.

62. **Long options and `-r module` before standard input.** `| node --input-type=module`, `| node --no-warnings`, `| node --no-warnings -`, `| ruby --disable-gems`, `| node -r esm -` and `| node -r ts-node/register` run standard input as code; `| node --input-type=module app.js` and `| node -r ts-node/register app.ts` are given a script file and do not. Amends 48, whose tail accepted short flags only. Closes: the ESM-from-stdin idiom reported as `DIES`.
